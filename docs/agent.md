# ایجنت مکالمه‌ای (Conversational Agent)

این سند معماری جدید ربات را توضیح می‌دهد: پیام آزاد → مدل با Function Calling →
اجرای ابزار یا پرسیدن تأیید → پاسخ طبیعی + حافظهٔ گفتگو.

## چرا تغییر کرد؟

نسخهٔ قبلی یک ربات «منو + ۱۹ فرمان» بود: کاربر باید دستور حفظ می‌کرد و هر درخواست
مسیر ثابتی داشت (`/new` ← تحلیل ← طرح ← دکمهٔ تأیید ← اجرا). خواستهٔ مالک این بود که
ربات مثل ChatGPT رفتار کند: پیام آزاد، درک نیت، استفاده از ابزار، و اگر ابزار/دسترسی
نبود، رد صریح و مؤدبانه.

## جریان یک پیام

```
Telegram update
   │
   ├── callback (ag|<actionId>|y|n) ──┐
   ├── «بله» / «خیر» در پیام آزاد ───┤
   │                                 ▼
   │                        ConversationalAgent.decide()
   │                        (اجرای ابزارهای تأییدشده + ادامهٔ حلقه)
   │
   └── پیام آزاد ─▶ handleFreeText()
                     ├─ گفتگوی قدیمی در انتظار (فقط /new و /resume)
                     └─ ConversationalAgent.respond()
                          ① ذخیرهٔ پیام کاربر در `chat_messages`
                          ② ساخت پیام‌ها: system + تاریخچهٔ D1 (حداکثر ۳۰ پیام)
                          ③ ProviderManager.complete({ tools })
                          ④ پاسخ متنی؟  → تمام (پاسخ برای مالک)
                          ⑤ tool call?
                              ├─ ابزار حساس و در دسترس → ردیف `pending_actions`
                              │                          + سؤال «آیا موافقی؟»
                              └─ در غیر این صورت → اجرا و برگشت نتیجه به مدل (حلقه)
```

حداکثر ۵ رفت‌وبرگشت با مدل در هر پیام (`maxSteps`) تا هزینهٔ رایگان کنترل شود.
هر رفت‌وبرگشت یک درخواست از سقف `AI_DAILY_REQUEST_LIMIT` مصرف می‌کند.

## ابزارها

| ابزار | حساس؟ | توضیح |
|---|---|---|
| `get_bot_capabilities` | خیر | فهرست واقعی ابزارها + در دسترس/در دسترس نبودن + مخازن ثبت‌شده + محدودیت‌ها |
| `list_github_repos` | خیر | مخزن‌های در دسترس توکن |
| `read_github_file` | خیر | خواندن فایل (با سقف حجم) |
| `create_github_repo` | **بله** | ساخت مخزن |
| `write_code_to_github` | **بله** | ساخت شاخه (در صورت نیاز) + کامیت فایل |
| `create_pull_request` | **بله** | ساخت PR |
| `run_tests` | **بله** | صف‌کردن اجرای تست از طریق GitHub Actions (فقط لیست مجاز، مصرف دقیقه) |

«حساس» یعنی چیزی بیرون از ربات تغییر می‌کند یا هزینهٔ Actions مصرف می‌شود. اجرای این
ابزارها از `execute()` رد می‌شود، اما `requiresApproval()` قبل از آن کل درخواست ابزار
را در `pending_actions` پارک می‌کند. بنابراین مدل نمی‌تواند با تولید متن، تأیید را دور بزند.

### افزودن یک ابزار جدید

1. در `src/agent/tools.ts` یک `AgentTool` بسازید: `name`, `description`, `parameters`
   (JSON Schema), `sensitive`, `summarize` (جملهٔ فارسی برای سؤال تأیید), `availability`
   (بدون شبکه؛ فقط بررسی کلید/دسترسی) و `run`.
2. در `createDefaultTools()` به آرایه اضافه کنید.
3. یک تست در `test/agent.test.ts` بنویسید که مسیر «در دسترس» و «در دسترس نیست» را پوشش دهد.

هیچ ابزاری نباید از `ctx` به تلگرام دسترسی داشته باشد؛ خروجی ابزار فقط برای مدل است و
پیام نهایی توسط مدل نوشته می‌شود.

## سیستم تأیید

- سؤال به زبان طبیعی («برای انجام این کارها اجازه لازم دارم: ۱. ساخت مخزن …»)
  همراه دو دکمهٔ «✅ بله» و «❌ خیر» فرستاده می‌شود.
- پاسخ متنی هم پذیرفته است (`classifyApprovalReply`): «بله»، «آره انجام بده»، «ok go ahead»
  در مقابل «نه»، «خیر»، «لغو»، «cancel». «باشه»/«ممنون»/«سلام» **تأیید نیستند** و
  عبارت‌های ترکیبی مثل «نه، انجام نده» به سمت **رد** تفسیر می‌شوند (سمت امن).
- تصمیم‌گیری اتمیک است (`UPDATE ... WHERE status = 'pending'`), پس دوبار «بله» یا
  «بله + کلیک دکمه» ابزار را **یک بار** اجرا می‌کند.
- تأیید ۳۰ دقیقه اعتبار دارد؛ پس از آن منقضی و بی‌اثر می‌شود. `/cancel` هم آن را لغو می‌کند.
- اگر مالک موضوع را عوض کند و ابزارهای تأییدنشده در تاریخچه بمانند،
  `normalizeHistory()` برای هر tool call بی‌پاسخ یک نتیجهٔ جانشین می‌سازد تا ترنسکریپت
  برای Gemini/OpenAI معتبر بماند.

## حافظهٔ گفتگو

جدول `chat_messages` (migration `0002_agent_memory.sql`) هر پیام کاربر، پاسخ دستیار و
هر tool call/result را ذخیره می‌کند (`message_json` شکل کامل و مستقل از ارائه‌دهنده).

- در هر درخواست ۳۰ پیام آخر بازپخش می‌شود؛ فراتر از ۲۰۰ پیام، قدیمی‌ترها هرس می‌شوند.
- `/reset` حافظه را پاک می‌کند.
- پرامپت سیستم ذخیره نمی‌شود و هر بار با وضعیت تازه (پروژه فعال، مخازن، تأیید در انتظار) ساخته می‌شود.

## ترجمهٔ ابزارها برای هر ارائه‌دهنده

| مفهوم | Gemini | OpenAI-compatible | Anthropic |
|---|---|---|---|
| تعریف ابزار | `tools[].functionDeclarations` | `tools[]` + `tool_choice: auto` | `tools[].input_schema` |
| درخواست ابزار مدل | `parts[].functionCall` | `message.tool_calls[]` | `content[].tool_use` |
| نتیجهٔ ابزار | `functionResponse` در turn کاربر | `role: "tool"` + `tool_call_id` | `tool_result` block |

آرگومان خراب (JSON نامعتبر) باعث کرش نمی‌شود؛ به `{ __raw: ... }` تبدیل می‌شود و ابزار
با پیام خطای فارسی برمی‌گردد.

## محدودیت‌ها (صادقانه)

- ساخت مخزن با **GitHub App** ممکن نیست (توکن installation این اجازه را ندارد)؛ ابزار
  صریح می‌گوید و پیشنهاد می‌دهد از PAT استفاده شود.
- اجرای کد دلخواه روی سرور وجود ندارد؛ تست‌ها فقط از طریق GitHub Actions و فقط با
  دستورهای `COMMAND_ALLOWLIST` اجرا می‌شوند.
- `run_tests` فقط برای مخزن‌هایی کار می‌کند که به‌عنوان پروژه ثبت شده‌اند (فایل workflow
  باید در مخزن باشد)؛ در غیر این صورت پیام «دسترسی ندارم» برمی‌گردد.
- حافظه و تاریخچه در D1 است؛ پاک کردن دستی جدول، حافظه را از بین می‌برد.
- مدل رایگان ممکن است ابزار را اشتباه انتخاب کند؛ به همین دلیل دفاع اصلی، لایهٔ کد است
  (`requiresApproval`, `availability`, `ToolInputError`)، نه اعتماد به متن مدل.

## مهاجرت

```bash
npm run db:migrate    # migrations/0002_agent_memory.sql را روی D1 اعمال می‌کند
```

جدول `chat_messages` و `pending_actions` اضافه می‌شوند؛ هیچ دادهٔ قبلی تغییر نمی‌کند.
`Store.init()` وجود `chat_messages` را بررسی می‌کند، پس نصب تازه هم بدون migration دستی
اسکیمای کامل را می‌سازد.
